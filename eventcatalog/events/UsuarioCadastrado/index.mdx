## Visão geral

Um novo usuário (PESSOA ou ONG) concluiu o cadastro. Dispara o e-mail de boas-vindas.

- **Publicado por:** Microsserviço de Usuários
- **Consumido por:** Serviço de Notificação
- **Quando é publicado:** Depois que o cadastro é gravado no banco do serviço de usuários e antes de devolver o token ao cliente. O envio do e-mail é um efeito colateral: se o broker ou o n8n falharem, o cadastro continua valendo.

## Mensagem

Toda mensagem tem o mesmo envelope: `id`, `nome`, `ocorridoEm` e `dados`. O conteúdo de `dados` é:

| Campo | Obrigatório | Descrição |
|---|---|---|
| `usuarioId` | sim | Id do usuário (ObjectId do MongoDB). |
| `nome` | sim | Nome do usuário. |
| `email` | sim | E-mail de destino das boas-vindas. |
| `tipo` | sim | Tipo da conta. |

Exemplo:

```json
{
  "id": "3b9a6f2e-7c1d-4e58-9a0b-5d2f8c41e7a6",
  "nome": "UsuarioCadastrado",
  "ocorridoEm": "2026-11-08T03:15:42.123Z",
  "dados": {
    "usuarioId": "665f1c2e8b3a4d0012ab34cd",
    "nome": "ONG Patas Felizes",
    "email": "contato@patasfelizes.org",
    "tipo": "ONG"
  }
}
```

O schema completo (JSON Schema) está na aba **Schema** desta página.

## O que o consumidor faz

O serviço de notificação monta o e-mail de boas-vindas (texto e HTML) e o entrega ao webhook do n8n, que envia por SMTP.

## Garantias e falhas

- **Entrega:** pelo menos uma vez (*at-least-once*). A mensagem é persistente e a fila é durável.
- **Falha no consumidor:** a mensagem recebe `nack` sem reenfileirar e vai para a fila `.dlq`, em vez de travar a fila ou se perder.
- **Broker fora do ar:** quem publica guarda o evento em memória e envia quando a conexão volta.
- **Dados pessoais:** só o nome do evento vai para o log; o conteúdo da mensagem não é registrado.
- **Versionamento:** esta é a versão `1.0.0`. Mudanças que quebrem o contrato devem criar uma nova versão do evento.
